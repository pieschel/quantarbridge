# QuantarBridge v0.1.5

Fixes the Raspberry Pi startup failure where the dashboard and DVM services
could become unavailable after restarting a configured installation.

## Configuration compatibility

- Setup now indents YAML list entries for the pinned DVM parser. It omits
  empty optional `presharedKey`, `rpcPassword` and `key` fields, which that
  parser rejected even though the YAML was valid. Nonempty secrets are retained.
- BrandMeister static-talkgroup synchronization writes `staticTalkgroups: []`
  when there are no subscriptions, rather than a YAML null value.
- The dashboard also tolerates legacy null static-talkgroup lists at startup.
- The persistence and direct-audio improvements from v0.1.4 are retained.

## Verification

The corresponding configuration and software corrections were applied to a
physical Raspberry Pi. After reboot the operator confirmed dashboard login
and retained settings; logs confirmed the V.24 modem, DVM services, local FNE
connections and BrandMeister login. No Quantar was connected, so RF/audio
verification at the radio site remains pending. This is not a physical boot
test of the newly packaged image.

CI and the ARM64 image build now parse freshly generated configurations with
the actual DVM parser, exercise empty talkgroup synchronization and dashboard
save/read round trips, and check that both original YAML failures are detected.
The image also validates DVM configuration after filesystem unmount/remount.
See the attached persistence, SSH/sudo and build reports.

## Installation

The new image contains the fixes. Initial SSH login is `qbadmin` /
`quantarbridge`; change the password and run `sudo quantarbridge-setup`.
Back up station settings before flashing: flashing replaces the SD card.

Updating program files alone does not rewrite already generated DVM runtime
configuration from older images. Existing affected installations also need
the empty optional fields removed and list indentation corrected, with a
backup first. Do not rerun setup with guessed station settings. The Raspberry
Pi repaired during the reported incident already received these corrections.
